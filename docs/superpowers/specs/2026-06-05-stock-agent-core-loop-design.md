# 股票小作手 — 设计文档（第一期：核心闭环）

> 创建日期：2026-06-05
> 范围：第一期「核心闭环」。第二期（自选/持仓/交易/复盘）、第三期（MCP 自动安装编排等）在文末列出范围，但有独立 spec。
> 一句话目标：把用户的 A/B 双系统操盘规则做成 agent 的「思维」，让它按规则分析 A 股、产出可记录的结构化报告，并在实战中教用户操盘；规则通过复盘不断进化，agent 随记忆/规则/战绩的积累而「成长」。

---

## 0. 定位

股票小作手不只是分析助手，而是用户的**股票老师 + 有成长性的操盘伙伴**：

- **助手**：按用户的核心规则分析股票，产出结论与仓位建议。
- **老师**：每次分析都附带教学，解释每条规则为什么这么定、命中意味着什么；在实战决策当口教用户操盘知识。
- **有成长性的伙伴**：随时间积累记忆、进化规则、累积战绩，表现越来越像懂用户、懂市场的老手。

**关于「成长 / 自主性」的底层事实（设计前提，必须达成共识）**：
agent 的「大脑」是无状态的 AI 调用，模型本身不会真的「学会」。
所谓**成长 = 系统为它积累的状态**，落在三本「账」上：记忆账（memory）+ 规则账（版本管理）+ 战绩账（成长档案）。
这三样越厚，它越像一个越来越强的老师。这是可靠可实现的「成长」，不是模型自我学习的玄学。

## 1. 总体架构

沿用 easy-Reader 的成熟形态：**Vue 3 + Node/Express + SQLite + TypeScript，单容器部署**。
新增一个 **Python 数据 sidecar**（封装 AkShare，以 MCP 协议对外）。

```
┌─────────────────────────────────────────────────────────┐
│  Vue 3 前端 (Pinia + composables)                         │
│  登录 → 初始化设定 → 规则版本 → 选股/分析报告 → (二期:复盘) │
└───────────────┬─────────────────────────────────────────┘
                │ REST  { success, code, data }
┌───────────────▼─────────────────────────────────────────┐
│  Node/Express 后端 (TypeScript)                           │
│  ├ auth         JWT (Access 30min + Refresh 30d), 多用户  │
│  ├ agent/       核心:自建推理循环                          │
│  │   ├ rule-engine.ts   硬指标确定性计算(代码算门槛)        │
│  │   ├ orchestrator.ts  组织"门槛结果+软料+规则原文"→报告   │
│  │   └ providers/       多AI插件(DeepSeek/Qwen/OpenAI/…)   │
│  ├ mcp/         MCP 客户端(开放协议)                       │
│  │   ├ data-client    连 Python AkShare MCP(可挂多个,兜底) │
│  │   └ browse-client  连 playwright MCP(抓研报/机构评级)   │
│  ├ skills/      自建"技能"模块(prompt + 工作流)            │
│  │   ├ memory     存/取 agent 记忆(对标 agentmemory)       │
│  │   └ research   探索需求/设计方案(对标 superpowers 理念)  │
│  ├ rulebook/    规则版本管理(structured gates + 散文)      │
│  └ data/        统一数据接口 + 缓存 + 数据源插件            │
└───────────────┬─────────────────────────────────────────┘
                │                          ┌──────────────┐
        SQLite (用户/规则版本/             │ Python sidecar│
        分析报告/数据缓存/记忆/战绩)        │ AkShare → MCP │
                                           └──────────────┘
```

**核心设计原则**：规则引擎用**代码确定性计算**硬门槛（ROE≥10%、PE<60、涨停>50…），
AI **只写软判断与结论叙述**，不负责算数字（避免数字幻觉，保证可复现）。
AI 可在「例外通道」覆写某条门槛，但**必须记录覆写理由**。

### 1.1 技术栈与约定

- 后端：Node + Express + TypeScript，`better-sqlite3`。
- 前端：Vue 3 + Pinia + composables（沿用 easy-Reader 的 stores/composables 结构）。
- 数据 sidecar：Python + AkShare，对外以 MCP server 暴露数据工具。
- API 响应格式（沿用 easy-Reader）：`{ success: true, code: "OK", data: {} }`。
- 部署：单容器（Express 同时服务 REST API 与编译后的 Vue 静态文件）+ Python sidecar 容器；`docker compose` 编排。

## 2. 规则的表示与版本管理（系统心脏）

用户的 A/B 双系统手册拆成**三段结构**，既给代码算，又给 AI 读。

### 2.1 规则版本数据结构（rulebook_version）

```
rulebook_version
├─ 元信息: id, user_id, 版本号(如 "V3.0"), 生效日, 作者(user|agent),
│          parent_version_id(可回溯/回滚), is_active, 创建时间
├─ persona: agent 人设文本(如「经验丰富的 A 股中线 + 短线操盘手」)
├─ gates[]        机器可读硬门槛(代码算)
│    每条: {
│      id, system: "A"|"B",
│      field: "roe_ttm",          // 取数字段
│      op: ">=", threshold: 10, unit: "%",
│      veto: true,                // 是否一票否决
│      exception_channel: {...}|null,  // 例外通道(满足这些才允许覆写)
│      teach: "为什么 ROE 要 ≥10%…"  // 教学层文案
│    }
├─ soft_rules[]   软判断(喂 AI 当判据,带教学层)
│    每条: { id, system, text, teach }
└─ position_rules 仓位/出场/熔断公式(结构化参数 + 公式说明)
     { single_trade_risk_pct, single_stock_cap_pct(A/B),
       system_total_cap_pct(A/B), stop_loss_rules, circuit_breaker, ... }
```

### 2.2 V3.0 基线（导入用户手册）

用户提供的《操盘实操清单 V3.0 双系统分家版》作为**初始 V3.0 基线版本**录入。已能结构化的部分：

**A 系统硬门槛 gates（②入场硬性排除）**：
- `roe_ttm >= 10` (%, veto)
- `pe > 0 && pe < 60` (veto)
- `pb < 5` (veto；重资产行业 < 1.5，作为行业例外参数)
- `ps < 8` (市销率, veto)
- `ma20 > ma60`（趋势向上）且「不在年内高点追高」（接近年内高点比例参数）
- 「真实利润 + 机构覆盖」（半结构化：有正利润可代码判，机构覆盖走软判断 + 抓取）

**A 系统大盘闸门（①）**：上证 20 日线 向上/走平/向下 → 决定可否开新仓 + 总仓上限（60%/40%/不加）。

**B 系统情绪闸门 gates（①，三条全满足才开 B）**：
- `涨停家数 > 50`
- `跌停家数 < 10`
- `上证 ma20 不向下`

**B 系统入场（②，soft_rules 为主）**：热点发酵 1–3 天内不追媒体铺天盖地；涨停后不破实体下沿且 `换手率 < 15%`；MACD 金叉初期/红柱放大；不接纯一字板。

**position_rules（A③④⑤ / B③④⑤ / 共用底座）**：
- 单笔风险：A=账户×1%，B=账户×0.5%；买入股数 =（账户×风险%）÷（买入价−止损价）。
- 单票硬顶：A 20%，B 10%；B 系统总仓 ≤ 30%。
- 出场：A 初始止损 −12% 或破支撑（收盘确认）、移动止盈沿 20 日线收盘破才走、基本面证伪清仓；B 时间止损 3 天不创新高、破 10 日线或 −6%、板块连续 2 天无涨停、大盘单日跌>2% 放量全清。
- 加仓：A 仅盈利 + 突破新平台；禁止向亏损补仓；B 禁止补仓。
- 共用熔断：当月亏 5% 停 3 天逐笔复盘；当月亏 8% 总仓降到 10% 以下。
- A 股机制提醒：T+1（止损最早次日生效）、一字跌停时单票硬顶才是真正风险上限。

### 2.3 版本进化流程

- 每个版本是**不可变快照**，`parent_version_id` 串成历史，可回溯、可回滚、可两两 diff。
- 复盘后（二期触发），agent 基于战绩账（胜率/盈亏比/期望值R/最大回撤）生成**新版本草稿** + 一段「改了什么 / 为什么」。
- 前端展示新版与当前 `is_active` 版的 **diff**。
- **用户点「采纳」**才把 `is_active` 切到新版（**agent 提议、用户审批才生效**）。
- 当前使用的永远是 `is_active` 那一版。

## 3. 数据层（最大风险点）

### 3.1 统一数据接口 + 多源 + 兜底 + 缓存

所有数据源都是往同一缓存层喂数据的**数据源插件**，互不冲突。读取走统一接口：先查 SQLite 当天缓存，没有才拉取，拉回即缓存（可回溯，每份分析报告钉死引用了哪天的数据快照）。

按数据类型分工（各用其所长）：

| 数据类型 | 变化速度 | 第一期来源 | 理由 |
|---|---|---|---|
| 行情/价量/均线/涨停跌停 | 每天变，要准要全 | ①手动上传 CSV（主）②定时爬取（兜底） | 通达信盘后行情最全最准最快、本地免费；涨停跌停家数可从全市场日线算出 |
| 基本面 ROE/PE/PB/PS/现金流 | 季度才变 | 半夜定时 AkShare 批量爬 | AkShare 财务指标更准更全；季报频率低，一晚一次足够 |
| 定性 研报/机构评级/综合判断 | 不定 | playwright 按需抓 + AI 归纳 | 非结构化，只能抓 + AI 提炼 |

### 3.2 三条数据通道（第一期）

1. **半夜定时任务（cron，盘后 ~23:00 数据已稳定）**：批量爬取全市场/用户自选池的**基本面 + 市场情绪**入 SQLite。白天分析直接读缓存，快且不撞限流。
2. **手动上传 CSV 行情**：用户在通达信盘后下载好行情、导出 CSV，前端上传 → 解析入库，覆盖当天**行情**。完全本地、零限流、最准。
3. **playwright 按需抓**：分析某只股票时才去抓它的研报/评级/综合判断。

> 通达信 `.day` 二进制直接解析放第二期；第一期先用「定时爬取 + 手动上传 CSV」两条路打通行情，AkShare 兜底保证系统不会因缺数据停摆。

### 3.3 Python AkShare MCP sidecar

- 独立 Python 服务，封装 AkShare，以 MCP server 暴露工具：基本面查询、日线/均线、涨停跌停统计等。
- Node 端用 `data-client` 作为 MCP 客户端连接；架构上可挂多个数据 MCP（未来 Tushare Pro 同接口接入），形成优先级/兜底链。

## 4. 分析流程 + 报告产物（核心闭环输出）

### 4.1 触发

用户输入一只或一批股票代码，选定 AI 模型、选定规则版本（默认 `is_active`），点「分析」。

### 4.2 流程

```
1. 取数   data-client 取:基本面(ROE/PE/PB/PS/现金流)、日线均线(ma20/ma60/年内高点)、
          市场情绪(当日涨停/跌停家数)。先查当天缓存,无则拉,拉回即缓存。
2. 软料   browse-client 用 playwright 抓研报/机构评级/综合判断,AI 归纳成要点。
3. 算门槛 rule-engine 按 is_active 规则逐条算:每条 gate 标 ✅/❌/⚠️,给实测值 vs 阈值
          (纯代码,数字不会错)。
4. AI下判 orchestrator 把"门槛结果表 + 软料 + 规则原文 + 人设 + 相关记忆"喂选定 AI,产出:
          A系统结论 / B系统结论 / 是否走例外通道(覆写带理由) / 仓位建议 / 一句话结论。
5. 落库   存成一份分析报告(report)。
```

### 4.3 报告数据结构（report）

```
report
├─ id, user_id, 创建时间
├─ stock_code, stock_name
├─ rulebook_version_id        ← 用了哪版规则
├─ data_snapshot_id / 日期    ← 引用哪天的数据快照
├─ ai_provider / model        ← AI 是谁
├─ gate_results[]             ← 逐条门槛: { gate_id, system, 实测值, 阈值, 状态:✅❌⚠️, 是否覆写, 覆写理由 }
├─ soft_findings[]            ← 软料要点(含来源链接)
├─ a_conclusion / b_conclusion / exception_channel
├─ position_suggestion        ← 仓位建议(按公式算)
├─ one_liner                  ← 一句话结论
├─ teach_notes[]              ← 教学层:每条命中规则的一句话教学
└─ raw_ai_response            ← 原始 AI 输出(可审计)
```

报告渲染成可读卡片（A 系统逐条表格 ✅❌⚠️、A 结论、B 情绪闸门、B 理论评估、总结表、一句话结论、执行建议），形态对齐用户提供的「300241 瑞丰光电」示例。可导出。

**每份报告钉死三件事**：用了哪版规则、引用哪天数据快照、AI 是谁 —— 为二期复盘的精确归因（触发了哪条核心原则）打基础。

## 5. 成长 + 教学模型（贯穿全系统）

### 5.1 老师角色 — 每份产物带「教学层」

- 报告每条命中的 gate 后附**一句话教学**（为什么 ROE 要 ≥10%、为什么 70 倍 PE 危险、为什么换手>15% 是出货嫌疑）。看一次报告 = 上一节实战课。
- **讲解模式（可选）**：agent 用苏格拉底式反问（「B 情绪闸门关着，你觉得现在该不该碰？」），用户答，agent 点评。教学发生在实战决策当口。
- **知识沉淀**：agent 把讲过的知识点、用户反复踩的坑写进 memory 技能，形成个人化教案。

### 5.2 成长 — 三本「账」越积越厚

1. **记忆账（memory 技能）**：市场观察、用户操作习惯、历次教训。下次分析可引用。
2. **规则账（版本管理，见 §2.3）**：复盘 → 提议新版 → 用户审批 → 进化。
3. **战绩账（成长档案）**：按 R 倍数、胜率、期望值、最大回撤逐月统计并画趋势 —— 「它在不在变强」的客观证据，对应用户 V3.0 手册「判断我是不是太保守的唯一客观依据」。

> 第一期：实现 memory 技能雏形 + 战绩档案**数据结构预留**；完整复盘驱动在二期。

### 5.3 自主性 — 「信任度档位」渐进放权（用户控制旋钮）

- 初期：**全提议制**（选股、买卖提示、改规则都只建议，用户拍板）。
- 当战绩账证明**连续 N 笔期望值为正**，系统提示可升档：允许 agent 自动把符合硬门槛的票推进自选池、自动预填订单、更大胆提改规则草稿。
- 放权永远是**用户手动升档，随时可降档**。autonomy 跟着已验证的战绩走。

> 第一期：信任度档位**数据结构预留 + 默认全提议制**；放权动作在二期。

## 6. 多用户与初始化

- 注册/登录：JWT（Access 30min + Refresh 30d），沿用 easy-Reader。
- 每用户独立的：规则版本历史、分析报告、数据缓存视图、记忆、战绩档案、AI 配置。
- 初始化设定向导：
  1. 设定 agent 人设（默认给「经验丰富的 A 股中线+短线操盘手」模板，可改）。
  2. 导入核心规则（默认载入 V3.0 基线，可在此基础上编辑生成自己的初版）。
  3. 配置至少一个 AI 提供方（API Key）。

---

## 7. 多 AI 插件

沿用 easy-Reader 的 `ai/` 插件模式，支持 DeepSeek / Qwen / MiniMax / OpenAI / Claude / Ollama 等。
用户为 agent 推理选定使用哪个模型；不同任务（下判、软料归纳、教学）可用同一或不同模型。
API Key 按用户存储（参考 easy-Reader 的 secret 管理）。

## 10. 一句话总览

> 股票小作手 = 把用户的 A/B 双系统规则编码成「代码算硬门槛 + AI 写软判断与教学」的分析引擎，
> 每次分析产出可审计、可归因、带教学的结构化报告并落库；
> 规则经复盘由 agent 提议、用户审批而进化；
> agent 靠记忆账 + 规则账 + 战绩账三本账「成长」，靠信任度档位由用户渐进放权。
